AnxOS Control Center v2.0 — Build 214

November 19, 2026

Build 214 makes Add a Server a real installation marketplace. Every card that says it installs was installed for real on a test PC before it shipped, and the ones that can't work yet say why instead of pretending.

  • 13 more game servers, each installed and started for real on Windows: ARK: Survival Evolved, ARK: Survival Ascended, Space Engineers, Core Keeper, V Rising, Enshrouded, Unturned, Satisfactory, Don't Starve Together, 7 Days to Die, Garry's Mod, Project Zomboid and Factorio (Factorio on Linux). Cards name the operating systems they were tested on; untested ones say so.
  • Databases, apps and media as Docker services: PostgreSQL, MariaDB, Redis, Grafana, Prometheus, Uptime Kuma, Gitea, Nextcloud, Nginx, Jellyfin (with a read-only media folder), Immich (as one Compose project), IT-Tools and Stirling PDF. Passwords are generated per install and shown once; AnxOS keeps no copy. Utilities are published on this computer only by default.
  • Deploy your own application: a Java .jar, or a zipped Node.js or Python project, runs as a managed app with start, stop, logs and resource use. The archive is checked before anything is created. AnxOS does not install npm or pip packages yet: bring node_modules with a Node.js project; a Python project that lists packages is refused with a message.
  • Discord.js Bot deploys your own zipped bot. Its bot token is stored encrypted by the AnxOS Agent and given to the bot as DISCORD_TOKEN when it starts; it is never saved in the bot's files or shown again.
  • Server secret store. Passwords a server needs at start (Project Zomboid's administrator, a bot token) are stored encrypted by the Agent, separately from the server's settings, files and backups, and removed from its console output.
  • Modrinth modpacks install and run. Every Modrinth pack failed with "server-pack runtime could not be resolved" since Build 193; AnxOS now installs the Minecraft and loader version the pack declares.
  • Minecraft servers on Windows PCs that have their own Java installed could fail to start ("executable is outside approved paths"); AnxOS's bundled Java is now chosen.
  • Python apps on Windows were never detected (the "python3" command there is the Microsoft Store shortcut).
  • Windows game servers started by name ("not found") and UDP-only servers stuck on Starting, including Valheim, Palworld and V Rising, now start and report ready.
  • Minecraft Bedrock (Docker) installs again; it needs the Minecraft EULA, which the wizard now asks for, and keeps its world.
  • Settings files are escaped: a quote or angle bracket in a server name can no longer add settings to a game's settings file.
  • Docker: busy ports are detected before anything is created, slow image downloads and container starts no longer fail as "Agent unavailable", and the volume list loads on computers with many containers.

AnxOS Control Center v2.0 — Build 213

November 17, 2026

Build 213 is about running more than one computer. You can see every computer's servers in one list, keep Agents up to date from the app, move a server between computers, and run AnxNet's relay and gateway on a server you own.

  • All computers in My Servers. One list of every server on every computer, with the computer each one runs on. Start, stop or restart several at once; stop and restart ask first. A computer that is offline keeps its servers listed as "last known".
  • Update Agents from the app. Agent Control can update Linux computers whose Agent was installed from the anxos-agent package, one at a time or all together. Each package is checked against the release's checksums first, and if the new Agent doesn't come up, the previous one is put back. An update is refused while that computer's servers are running.
  • Automatic Agent updates (off by default). Settings > Updates > Automatic Agent updates: choose which computers, which days and what time window, and whether AnxOS only tells you or installs the update. Every update is listed in its history. It never restarts an Agent while its servers are running.
  • Safer moves between computers. Before a server moves, AnxOS checks that the target is online, the server is stopped, the platform matches and there is room (ports, memory, disk, size). It won't start while a check fails. The backup is verified before it is sent and checked again when it arrives. After a clean move, AnxOS offers to switch over to the new copy.
  • Modpack updates. Servers installed from a Modrinth or CurseForge modpack say when a newer version of the pack exists for the same Minecraft version and loader. AnxOS tells you; it doesn't apply the update yet.
  • Download server files from your phone. Phone Access can download any file in a server's folder, byte for byte.
  • AnxNet edge on your own server. The AnxNet panel has Copy edge config, the edge checks its settings before it starts, and a step-by-step guide covers running it as a service (docs/ANXNET_EDGE_DEPLOYMENT.md).
  • A colourful Agent screen on Linux computers without a desktop.
  • Cancelling a server update before SteamCMD starts now stops it. Before, a Cancel during the pre-update backup, or while the update waited for another SteamCMD task, was acknowledged but the update could still run afterwards. With an Agent older than Build 213, the app offers Cancel only once SteamCMD is running and says why.
  • The phone no longer opens binary files as text. Tapping a .jar or an image opened it in the editor, where saving could have damaged it.
  • The AnxNet edge refuses unsafe settings, such as a public port range that includes SSH or the Agent's port, or a gateway without a public address.
  • The Download Manager no longer shows "cancelled" for an operation it couldn't stop.

AnxOS Control Center v2.0 — Build 212

November 16, 2026

Build 212 is a stability and security release. It fixes 143 defects found in a full review of the app, the Agent, Sharing and AnxNet. The only additions are recovery controls for problems it now detects.

  • Restore AnxOS Helper. If an update could not set the Helper up again (for example, the administrator prompt was declined), the app says so and restores it with one click.
  • Approve a changed SSH host key from the app instead of the connection staying blocked.
  • AnxNet shows when its identity is locked (its key could not be read) instead of silently creating a new one.
  • Crash-loop protection stops restarting a server that keeps crashing within ten minutes of starting, after three tries.
  • Servers that are running but not ready now raise a degraded alert.
  • Stop on Windows asks the server to shut down and save before forcing it.
  • Remote Agents can no longer be taken over from the network. Pairing and enrollment accept only the full Agent credential, not a short fingerprint of it. A freshly paired computer is protected at once instead of after its next restart. A computer you removed can only be paired again from that computer itself.
  • The Agent limits what an unauthenticated caller can make it do (request sizes are capped).
  • This PC's Agent credential is never sent to another computer, and node-credential recovery can no longer save it as a remote computer's credential.
  • A file dropped on the window can no longer replace the app.
  • An interrupted restore never leaves a server deleted. A full restore, and the rollback after a failed one, build the restored copy beside the server and swap it in. If the Agent stops in the middle (an update, a restart, a crash), it puts the server back when it starts again. Agent shutdown also waits for a running restore.
  • Updating AnxOS keeps the AnxOS Helper. If Setup cannot set it up again (for example, the administrator prompt is declined), the app offers Restore AnxOS Helper.

AnxOS Control Center v2.0 — Build 207

October 30, 2026

Build 207 makes AnxOS behave like a proper server app across several machines.

  • nodes stay reachable through SSH tunnels and Tailscale fallbacks;
  • every node's Agent can be started, stopped and restarted from Control Center, and only on the machine AnxOS has verified;
  • passphrase-protected SSH keys work for background tasks through the system SSH agent;
  • connection blips no longer flash nodes offline;
  • Playit is set up by linking an account instead of pasting an address;
  • the desktop app is reorganized, animated and lighter on the GPU.
  • Agent Start, Stop and Restart for remote Linux nodes. Agent Control now controls remote Agents, not only this PC's.
  • Verify Access before Agent control. SSH Start, Stop, Restart and Agent Update stay disabled until a read-only access check passes for the node and its SSH profile. The check signs in, confirms the machine reached is that node, finds the Agent service and checks passwordless control.
  • Protection against controlling the wrong machine. Every SSH Agent action and Agent Update first confirms that the machine reached is the node: its Agent's device ID, or its hostname when the Agent is stopped. If it isn't, nothing runs.
  • SSH keys with passphrases for background tasks. A key profile can use the system SSH agent (on Windows, the OpenSSH Authentication Agent; load the key once with ssh-add).
  • App-managed SSH tunnels for nodes. A node whose Agent listens only on the node itself (for example 127.0.0.1 on a VPS) can be reached through an SSH tunnel that Control Center opens, watches and reconnects with backoff. Tunnels use key authentication and a host key you have already approved; they never prompt or accept an unknown key.
  • Route fallback with Tailscale suggestions. A node can have up to four extra addresses. Control Center uses the first one whose Agent proves the paired device identity, so a different machine answering on an address is never trusted. "Find Tailscale route" suggests the node's tailnet address from tailscale status (read only).

AnxOS Control Center v2.0 — Build 206

October 8, 2026

Build 206 adds service-managed instances: the Agent can now observe and control an existing OS service (a systemd unit) without ever owning its process. The first use is adopting a production FiveM server that already runs as anxrp-fxserver.service, without any risk of the Agent launching a second copy.

  • Package: AnxOS-Agent-2.0-build206.deb, SHA-256 59842c83fd66d98084d991cd7d9769ef1e21f26d71dabd695049770394cb979f, built on Linux from the LF-exact archive of cc862de with only release.json changed to build 206 in the build copy.
  • The official Build 205 package (SHA-256 7b9410c0433332d30ebb0d8a0b73aed36902f30063ec36d74403e20e60357acd) is kept on that host as the rollback artifact.
  • That host's Agent must not be self-updated or upgraded until an official release containing this change exists. The official Build 206 package supersedes it. It is not identical: it adds the service operations layer (PR #2: serviceManagedOperations.js, the operations routes, safe-restart on the lifecycle permission tier, systemctl show --timestamp=unix), carries official provenance, and no longer ships a stray ssh2/lib/protocol/crypto/build/ directory that the temporary package picked up from the build host. Both share the dpkg version string 2.0-build206, so move a host from one to the other with dpkg -i (a same-version reinstall); apt will report it as already installed. Either way only the Agent service restarts; a managed service such as FXServer is never restarted by the package.
  • Service-managed instances (`type: "systemd-service"`). systemd stays the single owner of the process. The Agent runs only [sudo -n] systemctl start|stop|restart <unit> and systemctl show; it never spawns, signals or adopts the workload and holds no PID for it. Unreadable service state is shown as Unknown, never Stopped, and lifecycle actions refuse to act on it.
  • Operator-authored and allowlisted. The record is written on disk by an operator and cannot be created or edited through the API. The unit must also be listed in AGENT_SYSTEMD_UNIT_ALLOWLIST in the root-owned Agent environment file, and control is limited to exact commands pinned by a sudoers drop-in. See docs/SERVICE_MANAGED_INSTANCES.md.
  • Desktop support. Control Center shows these instances as "systemd service" / "Managed by systemd" with a notice naming the unit, a readable reason for Unknown and Failed states, and disables (with an explanation) everything the Agent refuses: console commands, force-kill, editing, renaming, duplicating, deleting, backups and scheduled restarts.
  • Capability report. The Agent health response gains an additive serviceManagedInstances capability listing the allowed units.
  • Service operations layer (second Build 206 pass). For a service-managed instance the Agent can now read, without owning anything: systemd's MainPID and uptime, AnxRP health (READY, version, boot id, sessions) from its status file, the connected player count from FXServer's loopback /dynamic.json and /players.json (names and identifiers are never stored or logged), the listening game ports from /proc/net, and an optional operator-written deployment manifest (unofficial-build flag, rollback artifact and backup status). New Agent environment variable: AGENT_SERVICE_STATUS_ROOTS.
  • Safe Restart. One guarded action that automates the proven Phase 5 flow: verify the instance, unit and MainPID, systemd health, AnxRP READY (fresh) and 0 players, writable history; re-check players; issue exactly one systemctl restart (never retried); wait for a new MainPID, the listening ports, AnxRP READY with a new boot id, and a settle window with no automatic restart. Anything unknown, unreadable or ambiguous refuses or fails closed. Plain start, stop and restart are locked while it runs.
  • Restart history. An append-only service-history.jsonl records every Safe Restart (started, then finished), every refusal and every plain start, stop and restart; interrupted operations are detected. A restart is refused if the history cannot be written.
  • Control Center. A SYSTEMD MANAGED badge and operations panel (MainPID, uptime, AnxRP state and boot id, players, ports, preflight checklist, progress, result, history, unofficial-build warning, rollback artifact and backup status, read-only journal in the Console tab) and a specific reason on every disabled control.
  • Port-conflict check failed open. The start preflight ignored listening sockets whose owner it could not identify (for example a server running as another user), counted a process owned by another user as dead, and swallowed errors from the check as "no conflict". Unknown owners and unreadable socket tables now block the start for every instance type.

AnxOS Control Center v2.0 — Build 205

September 26, 2026

Build 205 makes the Agent usable on a headless server and brings the same Agent runtime to every surface: the Control Center Agent Control GUI, the anxos-agent CLI/TUI, and the Control Center protocol/API. Pairing, identity, authentication, and lifecycle logic keep one authoritative implementation, and the safety defaults that protect a reachable Agent are unchanged.

  • Headless Agent CLI/TUI. A Linux server with no desktop can install the Agent and manage it from the terminal. Running anxos-agent opens the TUI, with subcommands for status, pair, service status|start|stop|restart, logs, diagnostics, update --check, unpair, --help, and --version.
  • Official Agent package. AnxOS-Agent-<version>.deb for Debian 11+/Ubuntu 22.04+ x64 (glibc >= 2.28), installed as the anxos-agent.service systemd system unit, with an AnxOS-Agent-<version>.deb.sha256 checksum file published alongside the package in sha256sum -c format so the download can be verified before install.
  • Add Computer, redesigned. Adding a computer now offers both paths — a desktop computer or a headless server — with the instructions and pairing steps for each, instead of a single ambiguous flow.
  • Pairing friction. The headless path no longer requires a source checkout or developer commands; pairing uses a one-time code from the TUI or anxos-agent pair, entered under Add Computer.
  • Honest status on headless nodes. Status, logs, and diagnostics come from the same runtime as the desktop surfaces, so a headless Agent reports the same state the GUI would show instead of a reduced summary.
  • Headless pairing presentation. The Agent CLI/TUI now shows the full pasteable pairing code — with the short ANX-XXXX-XXXX-XXXX kept separately as a reference code — exactly as Control Center redeems it, closing the golden-path gap where the short reference code alone was rejected as invalid.
  • Marketplace dependency recovery. Structured Marketplace errors now cross the Control Center IPC bridge intact (code, suggestion, and details.missingDependencies are preserved), so the "prepare node / missing Java" recovery path is offered instead of dead-ending.
  • Minecraft defaults and honest install outcomes. Minecraft templates now default to a Java-21-compatible version (1.21.11); Paper/Vanilla pre-flight refuses a version that needs a newer Java with a clear required-vs-available message; and an install whose started process crash-loops now fails honestly (START_FAILED) instead of reporting Complete.
  • Package upgrade applies immediately. Upgrading the Agent .deb now best-effort restarts the running service (systemctl try-restart) so the new payload takes effect without a manual restart; fresh installs are unchanged.
  • Safety defaults are unchanged. The Agent binds loopback (127.0.0.1) by default; enabling another computer to connect is an explicit opt-in. While a reachable Agent is not yet paired, anyone who can reach it could claim it, so pair promptly.
  • Pairing codes are one-time and valid for 10 minutes. Full tokens never appear in the UI, logs, or diagnostics; no authentication, authorization, loopback, or redaction check was weakened in this build.
  • Supported headless platforms: Debian 11+ and Ubuntu 22.04+ x64 with glibc >= 2.28. Other distributions and architectures are not supported.

Release Notes — AnxOS Control Center v2.0 build 203

September 17, 2026

Build 203 ships the V2-A Wave-1 close-out, the first V2-C and V2-D slices, and the authenticated browser management surface. It rides on top of the published Build 202 stable.

  • Shared instance identity model, authenticated agent enrollment handshake with nonce-protected start/complete/status paths, and fail-closed owner/admin/operator/viewer role enforcement.
  • Durable per-instance job lifecycle: state machine, idempotency keys, cancellation, audit events, and restart re-observation. A keyed repeat returns the original job; destructive operations are never replayed.
  • The agent spawn contract is now explicit: ANXHUB_CONFIG_DIR is the sole canonical identity source; legacy %APPDATA%\AnxHub bindings auto-migrate only during an explicit enrollment handshake.
  • A Windows/Linux support matrix documents what is tested, partial, and absent per platform.
  • Docker engine detection with per-prerequisite diagnostics (not installed, permission denied, daemon unreachable, socket access denied).
  • Container create/start/stop/restart/delete/pull ride the durable V2-A job store — a client restart can no longer orphan an in-flight container operation. Destructive container operations refuse idempotency keys.
  • A dedicated smoke pins the docker route manifest, capability report, prerequisite classification, and per-platform executable resolution.
  • Marketplace templates carry opt-in version stamps, sha256 checksums, and provenance (source) fields. Invalid metadata fails closed with distinct codes; the shipped 33-template catalog is unaffected.
  • Instances carry managed/imported/external ownership. Silent ownership flips are refused; adoption is an explicit one-way transition that stamps adoptedAt.
  • The instance detail panel surfaces ownership; imported and external services show an "Adopt service" action.
  • The dashboard gains a widget row (servers, remote systems, node health, metrics freshness) with a staleness policy: when the underlying data is not current, tiles show "Checking…" instead of a fake zero.
  • The agent serves a session-gated, read-only management page at /api/v1/ui. Sessions are short-lived (15 min), bounded (16 active), issued in exchange for the existing bearer credential or a one-time bootstrap code, and use HttpOnly + SameSite=Strict cookies scoped to the UI path.

AnxOS Control Center — Build 139

July 10, 2026

This release separates the desktop host, Agent nodes, and filesystem providers so Windows can reliably control local and remote machines.

  • Added stable Agent identities with duplicate-node detection and safe legacy configuration migration.
  • Made the application host a distinct local node instead of deriving This Device from the configured Agent URL.
  • Routed Dashboard, Monitoring, Docker, Instances, Files, SSH, Backups, Marketplace, and Security through the selected node.
  • Separated local, Agent-native, and SFTP filesystem providers so only explicit SFTP connections create SFTP sessions.
  • Added development routing diagnostics and regression coverage for node switching, persistence, migration, and filesystem routing.
